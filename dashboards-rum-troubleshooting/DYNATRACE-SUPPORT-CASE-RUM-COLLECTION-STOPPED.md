# Revisão interna — português

## Assunto sugerido

Atribuição incorreta de dados RUM Agentless ao frontend padrão `API Porto Seguro`

## Resumo do caso

Precisamos solicitar ao suporte da Dynatrace uma investigação de causa raiz porque o frontend web AngularJS `[RE]. Porto.re` deixou de apresentar novos dados de Real User Monitoring. A aplicação continua disponível aos usuários e os dados RUM continuam chegando ao tenant de produção, porém estão sendo atribuídos ao frontend `API Porto Seguro`, identificado na interface como o frontend padrão do ambiente.

Portanto, não se trata de ausência total de ingestão no tenant. O problema é que eventos e sessões da aplicação esperada não estão sendo associados ao frontend `[RE]. Porto.re`, o que produz a aparência de que sua coleta parou e impede a validação correta de novas sessões.

A aplicação utiliza JavaScript RUM inserido manualmente, no modelo Agentless, e é hospedada em Apache HTTP Server monitorado por OneAgent. O mesmo tenant Dynatrace de produção recebe dados dos ambientes de homologação e produção.

Uma alteração relevante foi realizada no process group do Apache: o RUM foi desabilitado com o objetivo de impedir uma possível segunda injeção automática, mantendo somente o JavaScript Agentless existente na aplicação. Precisamos que a Dynatrace determine se essa alteração causou ou contribuiu para a atribuição ao frontend padrão e identifique por que os dados deixaram de ser associados ao frontend correto.

## Impacto

- Novas sessões e eventos não aparecem no frontend esperado `[RE]. Porto.re`.
- Os dados da aplicação estão misturados aos dados do frontend padrão `API Porto Seguro`.
- Não é possível validar corretamente novas navegações, ações de usuários e sessões da aplicação.
- Session Replay e a correlação frontend/backend podem ficar associados ao frontend incorreto ou incompletos.
- A equipe não consegue validar com segurança alterações recentes na instrumentação.

# Dynatrace Support Case — English

## Subject

Agentless RUM data incorrectly assigned to the default `API Porto Seguro` frontend

## Summary

We are requesting a root-cause investigation because the AngularJS web frontend `[RE]. Porto.re` stopped showing new Real User Monitoring data. The application remains available to end users, and RUM data is still reaching our production Dynatrace environment; however, the data is being assigned to `API Porto Seguro`, which the Dynatrace UI identifies as the environment's default frontend.

This is not a complete tenant-wide ingestion outage. Events and sessions generated by the affected application are not being associated with the expected `[RE]. Porto.re` frontend. As a result, the expected frontend appears to have stopped collecting data, while its traffic is mixed into the default frontend.

## Business and operational impact

- New user sessions and RUM events do not appear under the expected `[RE]. Porto.re` frontend.
- Application data is mixed with data assigned to the default `API Porto Seguro` frontend.
- Recent user navigation and interaction data cannot be validated against the correct frontend.
- Session Replay and frontend-to-backend correlation may be associated with the wrong frontend or may be incomplete.
- We cannot reliably verify recent instrumentation changes.

## Environment and instrumentation context

- Application type: Web frontend / AngularJS.
- Web tier: Apache HTTP Server monitored by Dynatrace OneAgent.
- RUM instrumentation method: Manually inserted Agentless RUM JavaScript.
- Dynatrace environment: Production tenant.
- The same Dynatrace production tenant receives RUM data from both the production and non-production/homologation environments.
- Expected frontend: `[RE]. Porto.re`.
- Frontend currently receiving the data: `API Porto Seguro`, identified as the environment's default frontend.
- The application remains accessible and RUM data continues to reach the tenant, but under the wrong frontend identity.

## Relevant configuration change

RUM was disabled for the Apache HTTP Server process group to prevent a potential second automatic JavaScript injection. The manually inserted Agentless RUM JavaScript was expected to remain as the only browser-side instrumentation and to continue reporting to `[RE]. Porto.re`.

We now understand that disabling RUM at process-group level may disable capabilities beyond automatic JavaScript injection. We need Dynatrace Support to determine whether this change caused or contributed to the fallback/default frontend assignment in this specific Agentless/manual-insertion configuration.

## Expected behavior

When a user accesses the AngularJS application, the manually inserted RUM JavaScript should load and send RUM data to the configured Dynatrace environment. New user events and completed sessions must be associated with the `[RE]. Porto.re` frontend and its instrumentation ID.

## Actual behavior

The application can be accessed and RUM data reaches Dynatrace, but the resulting events and sessions are associated with `API Porto Seguro` instead of `[RE]. Porto.re`. The Dynatrace UI indicates that `API Porto Seguro` is the default frontend for the environment.
